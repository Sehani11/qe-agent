QE VERIFICATION AGENT

How the system works

The system reads a requirement from Jira, writes test scenarios from it, checks whether the code on GitHub actually implements them, and produces a report linking each requirement to its result.

The same thing in words

1

Read the requirement

The user pastes a Jira ticket ID or link. The system fetches the ticket and pulls out its acceptance criteria — the numbered statements describing what the feature must do.

2

Write test scenarios

An AI model converts each acceptance criterion into one or more Gherkin scenarios in Given / When / Then form. Each scenario records which criterion it came from, so nothing later has to guess. The user can edit them, or upload scenarios the team already wrote.

3

Check the code

The user points the system at a repository, a set of files, or a pull request. For each scenario the AI agent searches the code, opens the files that look relevant, reads them, and decides whether the scenario is implemented. It returns a pass or fail, an explanation, and a link to the exact file and line. If it fails, it also suggests what to add. If the agent could not read any code at all, the scenario is failed as not verified rather than guessed at.

4

Build the report

The results are assembled into a table linking each acceptance criterion to its scenario, its verdict, and the code that was examined — downloadable as PDF or CSV. No AI is involved at this stage, so the same session always produces the same report.

Two things the diagram leaves out on purpose. The system can also answer questions about a ticket or about the wider project, using the ingested documents as its only source. And the AI model in step 2 is swappable — a general-purpose model or a smaller one trained specifically on this task — which is what made the model comparison in the research possible. Both appear in the detailed architecture figures.
