7. **And** the existing fallback and response-shape guarantees still hold — endpoint unavailable degrades to `GeneralLLMFallbackProvider` with a warning, the `POST /api/v1/bdd/generate` response shape is byte-identical to general-LLM output, and no frontend file changes

## Context & Critical Background

### 🚨 The hardware will not make the 12s budget — plan for that, don't discover it

The dev machine's GPU is an **NVIDIA MX330 with 2 GB VRAM**. A 7B model at q4_K_M needs roughly 5 GB, so Ollama will run it substantially on CPU. Expect **30–90 seconds** for a two-AC generation, against a 12s budget.

This is not a bug and it is not fixable in this story's code. [serve/README.md](training/serve/README.md) already says it: *"A 7–8B model on CPU will not make that budget; serve it somewhere with a GPU, or accept that every request silently falls back."*

**What this means for you:** AC3 (a real fine-tuned generation) and AC4 (template match) are achievable locally and are the substance of this story. AC6 is a **measurement**, and "measured 47s on CPU, does not fit 12s, needs GPU serving" fully satisfies it. Do not raise `FINE_TUNED_MODEL_TIMEOUT_SECONDS` to make a green light — that value is load-bearing for NFR-P3, and Story 6.1's review spent real effort establishing it.

⚠️ **The provider's 12s bound will fire during your local testing** and fall back to the general LLM. Test the shim directly (`curl localhost:9000/`) to prove AC3's generation, and separately raise `SHIM_TIMEOUT_SECONDS` **only for that manual measurement**, never in committed config.

### The three conversion paths — researched 2026-08-09, all have traps

This is the story's real technical decision. Ollama cannot load a PEFT adapter as-is.

**Path A — Ollama's native `ADAPTER` with the safetensors directory.** Simplest by far:

```dockerfile
FROM qwen2.5:7b-instruct
ADAPTER /path/to/training/outputs/outputs/bdd-lora
```

⚠️ **Two documented risks.** Ollama's import guide lists supported adapter architectures as **Llama, Mistral and Gemma — Qwen2 is not among them**, so this may simply fail. And it warns *"it's best to use non-quantized (i.e. non-QLoRA) adapters"* — ours **is** a QLoRA adapter. Cheapest to try (minutes); try it first, but do not assume it works.

**Path B — `llama.cpp/convert_lora_to_gguf.py`, then `ADAPTER ./adapter.gguf`.** llama.cpp supports Qwen2 properly and handles LoRA adapters as self-contained GGUF files:

```bash
python llama.cpp/convert_lora_to_gguf.py --lora-path training/outputs/outputs/bdd-lora \
       --base Qwen/Qwen2.5-7B-Instruct --outfile bdd-lora.gguf --outtype f16
```

⚠️ Pass the **fp16** `Qwen/Qwen2.5-7B-Instruct` as `--base`, *not* the `unsloth/Qwen2.5-7B-Instruct-bnb-4bit` the adapter records — the script wants config and tokenizer, and the 4-bit repo is not the right source for them. `--base` downloads config only, not the full weights.

**Path C — merge into fp16, convert the whole model. LAST RESORT — only if A and B have both failed.** It removes every adapter-compatibility question, but costs a ~15 GB base download and a ~5 GB output, and Task 1 gates it behind recorded failures of the other two:

```bash
python -c "
from peft import AutoPeftModelForCausalLM
m = AutoPeftModelForCausalLM.from_pretrained('training/outputs/outputs/bdd-lora')
m.merge_and_unload().save_pretrained('training/outputs/merged')"
python llama.cpp/convert_hf_to_gguf.py training/outputs/merged --outfile bdd.gguf --outtype q8_0
```

⚠️ **Do not merge into the bnb-4bit base.** Merging LoRA weights into already-quantized weights and re-exporting loses quality silently. `AutoPeftModelForCausalLM` will try to load the base recorded in `adapter_config.json` — which *is* the 4-bit repo — so override it explicitly.

> **`training/serve/README.md` currently documents only Path C**, written before this research. Whichever path you take, correct that file (AC1). It is the file Story 6.3 will read.

**Base-model matching is not optional on any path.** Ollama's guide: *"Make sure that you use the same base model in the `FROM` command as you used to create the adapter otherwise you will get erratic results."* Ollama's `qwen2.5:7b-instruct` is a quantized build of `Qwen/Qwen2.5-7B-Instruct`; the adapter was trained on unsloth's 4-bit repack of the same weights. Same weights, different quantization. **AC4's template check will not catch a base mismatch** — it compares prompt templates, not weights. Erratic output that still parses is the failure mode to watch for.

### The contract, and why the shim already satisfies it

Read it off the code, not the epic — [fine_tuned_provider.py:88-116](backend/app/services/bdd_model/fine_tuned_provider.py#L88-L116):

```http
POST {FINE_TUNED_MODEL_ENDPOINT}
Authorization: Bearer {FINE_TUNED_MODEL_API_KEY}      # only when the key is set

{ "acceptance_criteria": "...",       # always
  "system_prompt": "...",             # only when non-empty
  "response_format": { …schema… } }   # only when provided
```

The shim at [training/serve/app.py](training/serve/app.py) implements exactly this and validates its own output before responding. Your job is to give it a model, not to change it.

Wire-up:
```bash
BDD_MODEL_PROVIDER=fine_tuned
FINE_TUNED_MODEL_ENDPOINT=http://localhost:9000/
```

### AC5 — the gap Story 6.1 handed forward, verbatim

From [6-1's Dev Notes](_bmad-output/implementation-artifacts/6-1-bdd-model-provider-abstraction.md):

> `FineTunedModelProvider` returns `response.json()` unvalidated ([fine_tuned_provider.py:73](backend/app/services/bdd_model/fine_tuned_provider.py#L73)). A wrong-shaped endpoint response surfaces as a confusing parse error in `bdd_service` rather than triggering fallback. Correct fix belongs to **Story 6.2**, when a real endpoint exists to validate against.

That endpoint now exists. Validate in the provider and treat a non-conforming body as a fallback trigger — same class as an HTTP error. Note the shim *also* validates; that is deliberate defence in depth, because `FINE_TUNED_MODEL_ENDPOINT` may point at something that is not our shim.

⚠️ **Do not add a field to `BDDGenerateResponse`.** Its JSON schema is handed to the model as `response_format`, so any new field becomes something the model is asked to populate. Story 6.1 hit this and documented it.

### Why `effective=fine_tuned` is the real proof (AC3)

A degraded run is **invisible in the UI** — the fallback returns perfectly good general-LLM scenarios in an identical shape. That is by design (AC7). The only signal is the attribution line [bdd_service.py:_log_attribution](backend/app/services/bdd_service.py):

```
bdd_model.generation session_id=… configured=fine_tuned effective=general_llm reason=endpoint_error
```

Story 6.1's review built this precisely so Story 6.3 could not mistake fallback output for fine-tuned output. **Check the log, not the screen.** A story that reports success on UI output alone has proven nothing.

### What the model is actually like — set expectations before you judge output

From [RUN_LOG.md](training/RUN_LOG.md): eval loss 0.3976, but **84% of the training corpus was testing-framework Gherkin** (behat, aruba, cucumber-*) about running CLI commands, not product behaviour. On an unseen AC pair the model produced structurally perfect JSON whose second scenario had a `when` identical to the first with the `then` merely negated.

**It learned the shape convincingly and the reasoning barely at all.** Expect valid, parseable, shallow output. That is the correct, documented baseline — **it is not a bug in your integration**, and it is exactly the question Story 6.3 exists to quantify. Do not chase it here.

## Dev Notes

### Anti-patterns for this story

- ❌ **Don't raise `FINE_TUNED_MODEL_TIMEOUT_SECONDS` to make AC6 pass.** It is 12s deliberately so the general-LLM fallback still fits NFR-P3's 30s. Story 6.1's review established this against a real bug
- ❌ **Don't judge success from the UI.** A silent fallback produces excellent scenarios. Only `effective=fine_tuned` proves anything
- ❌ **Don't rewrite the shim or the provider.** 43 tests cover them between `test_serving_shim.py` and `test_fine_tuned_provider.py`
- ❌ **Don't add a field to `BDDGenerateResponse`** — its schema is sent to the model as `response_format`
- ❌ **Don't commit the adapter, a GGUF, or a merged model.** `training/outputs/` is git-ignored; keep it that way
- ❌ **Don't jump to Path C because it "definitely works".** It is gated behind A and B for a reason: ~20 GB of traffic and disk to avoid a problem that the two cheap paths probably don't have
- ❌ **Don't blame the integration for shallow scenarios.** That is the documented corpus limitation, and Story 6.3's question
- ❌ **Don't touch `training/build_dataset.py`, `finetune_bdd.py`, or the notebook.** Story 6.5 owns those and they are `done`

#### 🐞 Two defects found in Story 6.5's shim — both blocked ACs, both fixed

**1. The chat-template check could never pass (blocked AC4).** `compare_templates` string-compared the adapter's **Jinja** template against Ollama's **Go** template. Different languages, so `mismatch` was guaranteed — a false alarm on exactly the case the check exists to bless. Measured: both emit the identical token set `['<|im_end|>', '<|im_start|>']` and all four roles, but share no source text.

  Fixed by comparing the **special-token skeleton** rather than source, and reporting *how* it was compared: `comparison: "exact"` for byte-identical, `"wire-format"` for equal token sets. A Llama-3 base under a Qwen fine-tune still fails loudly (`<|start_header_id|>` ≠ `<|im_start|>`), and two token-less templates are **not** a pass — they prove nothing. **This required editing `training/serve/app.py`, which the story's Project Structure Notes list under "Do NOT modify". Chamath approved the override before it was made.**

**2. The documented run command crashed on startup (blocked AC3).** `uvicorn app:app --app-dir training/serve` imports the shim *as* `app`, shadowing the backend's `app` package, so the shim's own `from app.schemas.bdd import ...` resolved to itself: `ModuleNotFoundError: No module named 'app.schemas'; 'app' is not a package`. The shim had **never actually been started** — Story 6.5 shipped and reviewed it on tests alone, and those load the file as `bdd_shim`, sidestepping the collision.

  Fixed by loading the schema by file path. The regression test runs a **cold subprocess**: an in-process version passed for the wrong reason, because by then pytest had already cached `app.schemas.bdd` in `sys.modules`. That first attempt was discarded rather than kept as a green test that checks nothing.

#### ⚠️ One story subtask was wrong and was deliberately not followed

Task 1 said *"The Modelfile's `TEMPLATE` must be the contents of `chat_template.jinja`"*. Doing that would have **caused** the failure it was meant to prevent: `chat_template.jinja` is Jinja and Ollama Modelfiles take Go templates. The stock `qwen2.5:7b-instruct` already ships the equivalent ChatML template, so it is inherited and then verified. The subtask is struck through in place rather than silently skipped.

Ollama's guide requires an identical base *"otherwise you will get erratic results"*. The README cited that warning only as why **Path A** fails and never recorded that **Path B carries the same exposure** — and AC4's template check provably cannot detect it, since it compares prompt formats, not weights. Left unwritten, Story 6.3 would attribute quantization drift to the fine-tune, which is the exact measurement it exists to make. **Fixed:** a dedicated "Known exposure" section in [serve/README.md](training/serve/README.md) with the two quantization schemes, why `/health` cannot catch it, the honest note that observed output is coherent (not evidence of no damage), and a concrete control for 6.3 — run the holdout against the adapter in `transformers` and compare, or take Path C if the result must be defensible.
- [x] **[Med] M1 — `compare_templates` reported `mismatch` for token families it cannot read.** Proven by execution: a *correctly served* Gemma-style pair returned `status: mismatch` with the incoherent detail *"trained emits [], served emits []"*, because `SPECIAL_TOKEN_RE` only matches `<|...|>` and empty-equals-empty fell through. **Fixed:** both-empty now returns `unknown` with a detail saying the checker could not read either template.
